# BuilderCRM — Construction CRM

A construction CRM built with React, TypeScript, Vite, Base UI, CSS Modules, React Router, TanStack Query, MobX and mobx-persist. Supabase provides Auth, PostgreSQL and the Data API; no separate Node.js server is required. Node.js is used for build and development tooling. The `minimatch` resolution pins the patched 11.0.4 release for lint tooling (GHSA-g3hv-75wg-m249).

## Requirements and development

- Node.js 24+, Corepack and Yarn 4.12.0, Supabase CLI 3.x.
- Docker for the local Supabase test stack.

```bash
corepack enable
yarn install --immutable
cp .env.example .env  # only when .env does not already exist
yarn dev
```

Configure these variables in the root `.env`:

| Variable                        | Purpose                                                                  |
| ------------------------------- | ------------------------------------------------------------------------ |
| `VITE_SUPABASE_URL`             | Public project API URL                                                   |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Browser-safe publishable key                                             |
| `SUPABASE_PROJECT_REF`          | Cloud project identifier                                                 |
| `SUPABASE_ACCESS_TOKEN`         | Scoped personal access token for the CLI; not an API secret key          |
| `DB_PASSWORD`                   | PostgreSQL password, mapped to `SUPABASE_DB_PASSWORD` by the CLI wrapper |

Only the two `VITE_` variables are bundled into the frontend. Never prefix an administrative secret with `VITE_`. `.env`, local test credentials, Supabase temporary files and build artifacts are ignored by Git.

## Architecture

- `src/app`: routing, providers, application shell and global theme tokens.
- `src/pages`: login, object list, object detail, task detail and assigned tasks.
- `src/features`: shared editing workflow and task table/filter workflow.
- `src/entities`: client models and task transition presentation rules.
- `src/shared`: generated database types, DTOs, generic API access, session plumbing, components and utilities.

There is no widgets layer. Imports use the `@/` alias. DTOs retain database field names; client models map dates to `Date` and identifiers to camelCase. React Router owns navigation and search parameters; TanStack Query owns requests, mutation state and server caching. Route loaders/actions intentionally do not duplicate that state.

Descriptions are stored as device-local drafts through MobX and mobx-persist. Keys include user ID, entity kind and record ID (or parent object ID for new tasks). Saving clears the draft. Logout clears cached server data and preserves user-scoped drafts. Names, addresses and assignments are not persisted as drafts. Themes use CSS variables and local storage; the initial theme follows the OS preference.

## Data model and security

The original cloud schema is captured in the baseline migration. Business tables are quoted PascalCase names: `Object`, `Task`, `TaskStatus`, `TaskStatusComment`, `Profile`.

- `Profile` links to `auth.users`, stores display name and one role: `supplier` or `assignee`. Only administrators may write profiles; user-editable Auth metadata is never trusted for authorization.
- Suppliers manage all company objects/tasks. Assignees can read only assigned tasks, related object information and history. They cannot change task fields or assignments.
- Task creation date is server-generated; date filters use Moscow calendar days. History times use `Europe/Moscow`.
- `Task.status` is an atomic current-state projection of the append-only `TaskStatus` log. `sequence` gives history deterministic order; `version` prevents stale mutations.
- One optional `TaskStatusComment` belongs to each transition. Returning work for revision requires a nonblank comment. Authors and timestamps are generated by the database.
- Soft deletion hides an object and all its tasks, or an individual task, through RLS. Physical deletion is not exposed; history foreign keys no longer cascade. Restoration is not implemented.

RLS is enabled on every public table. Anonymous access and authenticated direct writes are denied by grants and the absence of write policies. Reads are filtered by RLS. All writes go through four public **security-invoker** RPC wrappers:

| RPC                                                                             | Purpose                                                     |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `save_object(p_id, p_name, p_address, p_description, p_version)`                | Create with null ID or update a supplier's object           |
| `save_task(p_id, p_object_id, p_name, p_description, p_assignee_id, p_version)` | Create or edit a task; assignee must have the assignee role |
| `change_task_status(p_task_id, p_state, p_comment, p_version)`                  | Validate a transition and append history/comment atomically |
| `archive_record(p_kind, p_id, p_version)`                                       | Soft-delete `object` or `task`                              |

Privileged implementations live in the unexposed `private` schema. They deliberately bypass table write restrictions to append history and lock rows, so each checks the caller's identity, role and resource access explicitly. Their search paths are fixed, and PUBLIC/anon execution is revoked. There are no exposed security-definer functions. Both grants/RLS and RPC authorization are required; hiding buttons is not a security boundary.

Mutations lock the object before the task, serializing deletion and status changes for an object. Two operations with the same version cannot both succeed. A comment insertion failure rolls back the entire transition. No client-facing history update/delete RPC exists.

Status values retain the original enum spelling:

| From             | To               | Actor             | Comment  |
| ---------------- | ---------------- | ----------------- | -------- |
| Creation         | `new`            | Supplier          | —        |
| `new`            | `in progress`    | Assigned assignee | Optional |
| `in progress`    | `on review`      | Assigned assignee | Optional |
| `on review`      | `accepted`       | Supplier          | Optional |
| `on review`      | `under revision` | Supplier          | Required |
| `under revision` | `in progress`    | Assigned assignee | Optional |

## Manual user provisioning

There is no public registration screen or user-management UI. Public signups are disabled for the original project. For a new project, disable them in Supabase Auth settings or run `node --env-file=.env scripts/configure-auth.mjs`. Create **three suppliers and three assignees** manually:

1. Open Supabase Dashboard → Authentication → Users → Add user.
2. Enter each person's email and password and confirm their email. Use real, unique credentials; do not reuse local test credentials.
3. Open SQL Editor. Copy `supabase/manual-users.sql`, replace the six example emails/names with the actual users and run it. It validates that all six Auth users exist before assigning profiles.
4. Verify the returned six profiles. A user without a profile can sign in but sees the “profile not configured” screen and cannot access work data.

Only an administrator can reset passwords or assign/change roles. Existing task authors must remain resolvable; do not delete Auth users who have authored work records. Reassign tasks deliberately before changing an assignee's role.

## Local database and automated tests

```bash
supabase start -x realtime,storage-api,imgproxy,postgres-meta,studio,edge-runtime,logflare,vector,supavisor
supabase db reset --no-seed
yarn playwright install chromium
yarn test
```

`db reset` is destructive **only to this local test database**; never add `--remote` to that command. Tests have a hard loopback-host check. `yarn test` reads local keys from `supabase status`, creates/updates three users of each role locally, writes ignored `.test-env.json`, and starts Vite with the local API URL/key. It never provisions cloud users. Local passwords are randomized each run. Fixtures remain in the local database for debugging; reset the local DB when you want to remove them.

```bash
yarn test tests/security.spec.ts
yarn test tests/ui.spec.ts
yarn lint
yarn build
```

The Playwright suite covers the complete role × source × destination transition matrix, RLS isolation, direct API abuse, immutable history, comment atomicity, conflicting changes, reassignment, soft deletion, login, CRUD, filters, drafts and responsive themes. Reports are in `playwright-report/`; failure traces and screenshots are in `test-results/`.

## Migration workflow

Supabase CLI 3 targets the local stack by default; all hosted commands below explicitly use `--remote`.

For a new empty project, link and push all migrations:

```bash
yarn db link
yarn db db push --remote --dry-run
yarn db db push --remote --yes
```

For the **original project only**, the baseline was captured from its existing tables. Mark that baseline applied once, then apply the incremental migrations. Do not apply baseline DDL over the existing schema:

```bash
yarn db migration repair 20261105174141 --status applied --remote --yes
yarn db db push --remote --dry-run
yarn db db push --remote --yes
yarn db migration list --remote
yarn db db advisors --remote --type security
```

The initial incremental migration targets the verified empty original tables. For another existing project, inspect data and constraints and prepare a dedicated migration rather than using the repair command blindly.

For subsequent changes: iterate locally, run security advisors, generate a migration with `supabase db pull <name> --schema public,private --yes`, review its SQL (including grants), replay all migrations locally, and run tests before pushing. Hand-authored migrations must be created with `supabase migration new <name>`. Multi-statement SQL can be executed locally through `docker exec -i supabase_db_2b-studio-test psql -U postgres -d postgres -v ON_ERROR_STOP=1 -1 < file.sql`; the CLI query command may use prepared statements that reject multiple commands.

Regenerate DTO source types after schema changes. The script loads the root `.env`, preserves the generated-file notice, formats the output, and only replaces the file after successful generation:

```bash
yarn db:types          # Local database
yarn db:types --remote # Linked cloud project
```

Do not edit already deployed migrations. Add forward migrations. Preserve backup/restore procedures for future production data; application soft deletion is not a database backup.

## Build and deployment

```bash
corepack enable
yarn install --immutable
yarn build
yarn preview
```

The deliverable is `dist/`. It is built with the cloud URL and publishable key from `.env`; tests override those only in their child processes. Environment changes require a rebuild. Upload the contents of `dist` to the root of your static host. No Node.js runtime is required.

Configure history fallback to `index.html` for unknown application routes so refreshes on `/objects/:id` and `/tasks/:id` work. For nginx:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

Use HTTPS. Set Supabase Auth Site URL to the deployed origin and configure redirect URLs if you later add email recovery/invitation flows. Current login uses email/password and does not depend on a callback route. The application assumes hosting at `/`; subdirectory hosting requires coordinated Vite `base` and router `basename` changes.

## Operational checks

After deployment, sign in as both roles, create an object/task as supplier, complete a transition as its assignee and confirm the history. Check Supabase Auth/database logs for failures and rerun security advisors after migrations. The frontend shows request failures as Toasts and offers retry states for failed queries.
